在这之前，我用 agent 的方式大概是：想到什么就打什么，它做出来了就收下，做歪了就骂一句再让它重来。能用，但说不上"会用"。

今天花了大半天，跟着 Claude 把 Anthropic 官方的《Prompting best practices》和《为 Claude Sonnet 5.5 编写提示》从头啃了一遍，又顺带问了 CLAUDE.md 怎么写、任务怎么拆、怎么让 agent 自己证明活干完了。读完最大的感受是：**我以前缺的不是提示词技巧，而是"把它当成一个需要被交代清楚的同事"这个意识。**

这篇记一下我读到了什么，以及被一场小测打回原形的过程。

## 一、它是个聪明的新同事，不是读心术

文档开篇的比喻我很喜欢：把 Claude 当成一个**非常聪明、但刚入职、不了解你们规范和工作流程的新员工**。你说得越精确，结果越好。检验办法也很朴素：把你的提示词给一个不了解背景的同事看，他看不懂，模型也看不懂。

顺着这个比喻，后面很多条就都说得通了：

- **解释原因，而不是只下命令。** 与其写"绝对不要用省略号"，不如说"你的回答会被语音引擎朗读，它不知道省略号怎么念"。知道了为什么，它会自己举一反三。
- **想要它多做，就明说。** 只说"做一个数据看板"和"做一个数据看板，尽可能多加入相关功能和交互"，结果差别很大。新模型是严格按字面理解的。
- **想让它动手，就用动手的说法。** "能不能建议一些修改"，它真的就只给建议。要改就说"修改这个函数"。
- **别吼它。** 以前为了让旧模型多用工具，大家习惯写 `CRITICAL: You MUST ALWAYS...`。新模型对系统提示更敏感，这种语气只会让它用过头。
- **用 XML 标签分区。** 指令、资料、示例、用户输入各自包起来，模型就不容易把资料里的某句话当成你的命令。

这些单看都像常识，但回头看我自己的用法，几乎每条都踩过。

## 二、effort 不是"想得多就好"

Sonnet 5.5 那篇花了很大篇幅讲 effort。我一开始以为它就是"思考强度"，后来才明白它管的是这一轮回答愿意花多少 token，包括思考、正文，甚至工具调用的次数。

几个让我印象很深的点：

- 从 `medium` 起，模型几乎每次回复前都会简短思考，**连打招呼也是**；只有 `low` 才会在简单请求上跳过思考。
- **在系统提示里写"少思考一点"并不能可靠地减少思考量。** 要少想，就降档位，而不是靠嘴说。
- 中途切换顶层 effort 会让提示缓存失效，要在对话中途换挡，得用"按消息更改 effort"，而且这条换挡消息是**你的程序插进去的**，不是模型自己判断的。这点我追问了好几轮才想通：API 是无状态的，`messages` 里有什么，完全由你的代码决定。

中间我还被带着绕去问了"模型的直觉到底是什么""Transformer 怎么预测下一个 token"。看起来跑题，但正是这段让我理解了为什么结构化输出里不给它打草稿的空间，它就容易算错：写到 `{"total": ` 的时候，它前面什么推算都没有，只能凭一次预测"冒出"一个数。

## 三、长任务靠的是交接，不是记性

讲到智能体长任务那一节，我一开始完全看不懂，Claude 换了个"轮班工地"的比喻才讲通：

模型的上下文窗口是有限的，长任务必然要分很多"班"完成，而每一班的模型都不记得上一班的事。所以要像管工地一样，提前准备好交接材料：

- **验收清单**：结构化的测试，比如 `tests.json`，并且强调不许为了通过去改测试；
- **开工脚本**：`init.sh`，新窗口一键恢复环境；
- **进度笔记**：零散进展用自由文本；
- **施工日志**：git，天然带存档点，可以回滚。

还要告诉它"会有人接班，按节奏干"，不然它感觉窗口快满了，就会草草收尾，留一份清单给你。

我当时的总结是：长任务做好上下文管理与交接，写好测试，就不必担心开新窗口浪费时间。Claude 补了一句我觉得很关键的话：**交接材料要让模型自己边干边维护**，而不是我手动去写。

## 四、AGENTS.md：把"交代"写进仓库

既然每次都要交代，那能不能写一次就够？这就是 `CLAUDE.md` / `AGENTS.md` 的意义：放在仓库里的一份说明书，每次会话开始自动加载。

写法的核心是**短、具体、只写它自己猜不到的东西**：常用命令、目录结构、和默认习惯不同的约定、容易踩的坑。不要写"注意代码质量"这种正确的废话，也不要把整份 README 塞进去，它每次都占上下文。

关联方式也很简单：主内容写在 `AGENTS.md`，`CLAUDE.md` 里只写一行 `@AGENTS.md`，其他工具和 Claude 共用一份。也可以用软链接，但 Windows 上要折腾权限，我就不考虑了。

还有一句我想记住：**把它当成活文档。** 发现 agent 反复犯同一个错，就补一条；发现某条规则从来没起作用，就删掉。

## 五、任务拆分和"自证"

这两个问题是我读完之后单独问的。

**拆任务**，核心叫提示链：一个复杂任务拆成几步，每步只做一件事，上一步的输出用 XML 标签包好交给下一步。比如分析合同：先提取条款，再评估风险，最后写建议邮件。每一步都更专注，出了问题也知道是哪一环坏了。用 Claude Code 写代码时也是同样的思路：先读代码、出计划，确认后再分步实现，每一步都能单独验证。

**让 agent 自证**，是我觉得对自己最有用的一条。Claude 会在工作"看起来完成"时停下，如果没有可运行的检查，"看起来完成"就是唯一信号，**我自己就成了验证环节**，每个错误都要等我发现。

所以要给它一个能跑出"通过/失败"的东西：测试、构建、lint、截图对比，让它干活、跑检查、读结果、迭代到通过。按"多硬地卡住它"分四档：

1. 在提示词里叮嘱"改完跑测试，不过就继续修"，靠它自觉；
2. 用 `/goal` 设目标，每轮由独立评估器检查；
3. 用 Stop hook 跑脚本，不通过就不让结束，结果是确定的；
4. 让一个全新的子代理去挑错，干活的和打分的不是同一个。

越往后前期配置越多，但我就越可以走开。还有一句话我想一直记着：**要证据，不要声明。** 让它给我测试输出、跑了什么命令、返回了什么，而不是一句"已完成"。

## 六、一场不及格的小测

读完我很自信，就让 Claude 出 10 道具体的工程场景题，答完严格打分，80 分以上算通过。因为我觉得概念题太容易蒙对。

结果只答了三道：

| 场景                                     | 得分 |
| ---------------------------------------- | ---- |
| 1. 客服机器人说"你好"都要等几秒          | 60   |
| 2. 旧提示里的 `MUST ALWAYS use search` | 55   |
| 4. 编码 agent 干活时界面一片空白         | 40   |

第三题我还答串了，把场景 4 的答案当成场景 3 交了上去。

扣分点很具体：第一题我把 effort 档位和 `between_tools` 两个独立开关混在了一起，还以为 medium 就能解决打招呼延迟；第二题我从"永远搜索"改成"非必要不搜索"，恰好是文档点名要删的那类措辞，从一个极端摆到了另一个极端；第四题我只说了"要让用户看到进度"，没说出进度块在默认设置下文字是空的，也漏掉了题目里那句"把所有发现留到最后统一汇报"的旧指令。

我问它为什么我总是有遗漏，它给了四条，句句扎心：

1. **我在用"印象"答题，而不是用"机制"答题。** 读完一大篇文档，脑子里留下的是大意，而工程问题恰恰卡在细节上。认得出来和自己说出来，是两种不同的掌握程度。
2. **我没把题目里的细节当线索。** 出题人放进去的细节几乎都是考点。
3. **我找到一个解法就停了。** 文档给的方案通常是分层的：根因、配置、提示词、程序兜底、代价和验证。
4. **节奏太快。**

它给了一个答题框架，我觉得以后排查 agent 的问题也能用：**症状 → 根因 → 配置层 → 提示层 → 程序层 → 代价和验证**。

## 七、所以我打算怎么改

这次最大的收获不是记住了多少参数，而是意识到"读过"和"会用"之间还隔着很远。Claude 最后说，重复阅读的效果不如重复回忆和应用，最好的巩固方式是在真实项目里用一次。

那就从手边的事开始：

- 每个项目都配一份 `AGENTS.md`，并且当活文档维护。这个博客仓库里已经有一份，接下来就让它在一次次踩坑里长起来；
- 下指令前先想清楚：我要它动手还是给建议？为什么要这样做？做完怎么算对？
- 不接受"已完成"，只接受证据；
- 过一两天，不看文档，把剩下的七道题补完，再看能不能过 80 分。

到时候再写一篇，算是这篇的续集。
